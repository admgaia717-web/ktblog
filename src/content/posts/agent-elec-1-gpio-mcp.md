## ハードウェアは長いこと、人間の指のために設計されてきた

はんだごてを持つのは人間だ。ブレッドボードに線を挿すのは人間だ。マイコンにファームウェアを書き込むのも人間だ。AIはその様子を画像で見て、「配線ミスがありますね」とコメントするだけだった。

それが、変わる。

2026年、AIエージェントが自分の手で——正確には自分の「道具呼び出し」で——電子回路を操作し始めている。言葉がGPIOを High にする。指示がPWMのデューティ比を変える。それは地味なニュースに見えて、工作の世界では恐ろしく大きな転換点だ。

本連載「エージェントと電子工作、工作」は、この転換を追う。毎回1つの実例を解剖し、再現可能な部品を示し、奈良の教室で何を教えるべきかまで落とし込む。第1回は、その根幹を支える二つのオープンソース、**MCP-U**と**ESP32-MCP**だ。

## MCPという共通言語（1分版）

話はProtocolから始まる。

Anthropicが2024年末に提唱した **Model Context Protocol（MCP）** は、AIエージェントが外部の道具を呼び出すための共通規格だ。JSON-RPC 2.0の上に `tools/list`（何ができるか一覧する）と `tools/call`（道具を実行する）を載せただけの、薄いプロトコルである。

薄いのが良い。薄いから、5ドルのマイコンに載る。

▶ 関連動画: [AI Agents with MCP Explained（YouTube）](https://www.youtube.com/watch?v=wGz955ZeLpc)

MCPが普及するまで、AIにハードウェアを操作させるには「そのデバイス専用のグルーコード」を毎回書く必要があった。デバイスが変われば書き直し。メーカーが違えば最初から。工作のたびに翻訳者を雇うようなものだ。

MCPはその翻訳を、一度で済ませる。エージェント側は「MCPで喋れるもの」と認識すればよい。デバイス側は「MCPで喋れるよう」整備すればよい。あとは仕様が仲介する。

つまり——工作物が、エージェントから見える「道具」になる。

## MCP-U — Arduino互換マイコンが、AIから操れる

まず1つ目。タイの2edge.coが開発する **MCP-U** は、「AI対応マイコンのための統一インターフェース」を標榜するArduinoライブラリだ。

やっていることは驚くほど単純である。Arduino互換マイコンのGPIO、PWM、ADC、I2Cといったペリフェラルを、そのままMCPの「道具」として外部に公開する。USBシリアルでも、Wi-Fi TCPでも、Bluetoothでも、`Stream` につながるものなら何でもトランスポートに使える。ツール名のハードコードは不要で、AIエージェントが実行時に `tools/list` で自主発見する。

コードはこれで終わる。

```cpp
#include <MCP-U.h>

McpDevice mcp("my-device", "1.0.0");

void setup() {
  mcp.add_pin(2,  "led",    MCP_DIGITAL_OUTPUT, "Built-in LED");
  mcp.add_pin(34, "sensor", MCP_ADC_INPUT,      "Light sensor");
  mcp.add_pin(19, "motor",  MCP_PWM_OUTPUT,     "Motor speed (0-255)");
  mcp.begin(Serial, 115200);
}

void loop() {
  mcp.loop();
}
```

3本の `add_pin` 以外は、普通のArduinoスケッチと変わらない。このスケッチを書き込んだマイコンに、ホスト側からこう繋ぐ。

```
claude mcp add mcpu -e SERIAL_PORT=/dev/ttyACM0 -- npx mcpu-client
```

これで完了だ。エージェントから見れば、`led` は点けられる道具、`sensor` は読める道具、`motor` は速度を指定できる道具である。日本語で「LEDを点けて、明るさセンサーの値を教えて」と頼めば、エージェントが `tools/call` を組み立てて、基板上の現物が従う。

![Arduino Uno R3](https://assets.st-note.com/production/uploads/images/321080715/rectangle_large_type_2_32389543913ff7d39d6946c5a8ac666f.jpg)

ピンの型も実用的に揃っている。`MCP_DIGITAL_OUTPUT` はLED・リレー・ブザー、`MCP_DIGITAL_INPUT` はボタン・リードスイッチ・人感センサー、`MCP_PWM_OUTPUT` はモーター・サーボ・調光、`MCP_ADC_INPUT` はサーミスタのようなアナログ入力。電子工作の初歩の部品が、ほぼ網羅されている。

Arduino IDEのライブラリマネージャで「MCP-U」を検索してインストールできる。依存はArduinoJson v7だけ。教育的な配慮と呼んでよい。

![ESP32-C3ボード](https://assets.st-note.com/production/uploads/images/321080674/rectangle_large_type_2_d270089e5dd45dda0972d17aa00e2109.jpg)

## ESP32-MCP — サーバーごとマイコンに載せる

2つ目は、発想を逆にした実装だ。PedroFnsecaの **ESP32-MCP** は、MCPサーバーそのものをESP32の上で動かすC++ライブラリである（MITライセンス、2026年8月公開）。

特徴は3つ。

- **MCP 2026-07-28プロトコル準拠** — `initialize`、`ping`、`tools/list`、`tools/call` をフルサポート。ステートレス仕様に沿っている
- **組込みファーストの設計** — メモリ制約の厳しいESP32向きに、ArduinoJson v7でアロケーションを最小化
- **内蔵HTTPトランスポート** — `POST /mcp` で受けるHTTPサーバーが標準添付。CORS対応済みで、そのままLANに晒せる

アーキテクチャ図は美しいほど素直だ。ユーザーアプリケーション→MCPServer（道具登録）→MCPプロトコルエンジン→JSON-RPC 2.0層→トランスポート層。プロトコルエンジンとネットワーク輸送が完全に分離されているので、HTTP以外にも載せ替えられる。

つまりこういうことだ。MCP-Uが「マイコンを道具として見せる」道なら、ESP32-MCPは「マイコンそのものをサーバーにする」道。クラウドのAIでも、LAN内のローカルLLMでも、HTTPでPOSTすればESP32が応答する。中央サーバーが要らない。工作棚のチップが、ネットワークの端点になる。

## なぜ「今」なのか — ローカルLLMと5ドルの基板

技術的には前から可能だった、という反論は正しい。シリアル通信もJSONもGPIOも、全部20世紀の遺産だ。

足りなかったのは3つのピースである。

1. **プロトコルの事実標準**（MCP）— 主要なエージェントが皆喋るようになった
2. **載る implementations**（MCP-U、ESP32-MCP）— ライブラリを入れるだけで装置側が対応する
3. **安い頭脳**（ローカルLLM）— Raspberry Pi 5が量子化モデルを動かし、スマートホームの制御をプライバシー前提で完結させる時代になった

3つ目は見落とされがちだが、本質的だ。工作の現場にクラウドAPIは重い。庭の水やり装置の判断に、往復レイテンシも課金も要らない。Pi 5の4GB/8GB RAMとPCIe、3〜4Wの熱設計は、小さなLLMを常駐させるには十分になった。ローカルLLMがエージェントとして振る舞い、MCPで隣のESP32を操る。この構成は、もう「趣味の実験」の域を出ている。

## 設計と製造も飲み込む — Flux CopilotとAgentsCAD

さらに面白いのは、エージェントの侵食が「操作」に止まらないことだ。

基板設計の **Flux** にはAIチームメイト **Copilot** がいる。回路図をレビューし、データシートを読み、基板を配線まで手がける。プラットフォーム上で12万件以上の基板設計が完了している。

3Dプリントの世界では **AgentsCAD**（2026年7月、arXiv）が、FDM造形部品の設計をマルチエージェントLLM推論と幾何特徴認識で自動化する。注目すべきは、LLMが「数学的に不可能な回転」を平然と提案するハルシネーション問題に対し、**MCPツールとして精密計算関数を呼ばせる**設計で、物理的な裏付けを確保した点だ。プロトコルが、幻覚対策になっている。

![はんだ付けベンチ](https://assets.st-note.com/production/uploads/images/321080804/rectangle_large_type_2_299b0738e0abc373fd4c419898c7cd23.jpg)

Bambu Labプリンター向けにはエージェントスキル（bambu-studio-ai）も出ている。「32mmパイプ用の壁ブラケット、M4ねじ穴2つ、PETGで」と頼むと、モデリングから造形指示まで持っていく。

上から順に見ると、**設計（CAD）→ 配線（PCB）→ 造形（3Dプリント）→ 操作（GPIO）** の全層に、エージェントの足場が置かれた。工作のワークフロー全体が、言葉で駆動できる。

## 奈良の教室から — 16歳、ドローン、そして「工作」の再定義

この流れは、奈良で動いている教育の計画と真っ直ぐに交差する。

階戸奈良市会議員と萩原さん（ドローン事業家）らが進める構想では、ドローン×プログラミング×生成AIの教室を、片親・生活困窮家庭の高校1年生（年度30人規模、市の補助金事業）に開く。16歳から取れる無人航空機の操縦者資格が、そのまま仕事に繋がる回路を作る。部活動の地域クラブ移行にも「ドローンクラブ」を乗せる。

ここに本連載の主題を足すと、教室で教えるべき「工作」の定義が変わる。

かつての工作は、手を鍛えることだった。はんだの盛り方、ニッパーの角度、失敗したユニバーサル基板の匂い。それは今も尊い。だが16歳が就業で戦う2030年代、工作の中心は「機械に工作させる技術」に移る。プロンプトが設計図で、MCPが工具箱で、エージェントが見習い職人だ。

萩原さんの教室の1階にある2つの部屋。そこで「LEDを点けるには」を教えるとき、子どもたちは `add_pin(2, "led", MCP_DIGITAL_OUTPUT, ...)` を書くことになるかもしれない。コードは短い。しかしその短さは、AIと物理世界の間の翻訳を、もう人間が書かなくてよい、という意味での短さだ。

## 安全装置の話 — ハルシネーションは煙を出す

楽観だけでは記事にならない。物理世界には、誤答のペナルティがある。

ソフトウェアのバグは例外を投げる。ハードウェアのバグは煙を出す。エージェントが幻覚のパラメータでモータードライバを駆動すれば、FETが焼ける。ADCの最大電圧を誤認すれば、センサーが死ぬ。逆起電力を無視したリレー制御は、マイコンのGPIOを一撃で持っていく。

だから実装では、3層の安全が要る。

- **電気的ヒューズ** — ソフトウェアは必ず過電流に負ける、という前提の配線
- **範囲制約** — MCPツール側でPWMデューティやADC閾値の許容範囲を固め、エージェントの指示値をクランプする（AgentsCADのMCPツールによる計算強制と同種の思想）
- **人間の承認ゲート** — 初回の `tools/call` は人間が押す。慣れてから自動化の範囲を広げる

「AIに任せた」の結果が焦げた基板では、誰も得をしない。工作の伝統にはもともと「火の元に届く前に点検する」という作法がある。それをプロトコルの時代に翻訳するだけだ。
